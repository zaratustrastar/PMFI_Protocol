4) maxLossBps is “per update”

You’re right: with per-update checks, someone who can influence updates (or an owner mistake) could ratchet changes.

But realistically, if only the oracle signs, outsiders can’t spam updates unless you expose a public “updateNav” call anyone can trigger.

MVP fix (simple):

enforce a minimum update interval (e.g., “at least 30s/60s between accepted rounds”)

or enforce “timestamp must be >= lastTimestamp + X”

ops stability note

Your “API partial outage protection” is currently “bot errors, no signing.” That’s fine — but then on-chain functions that require navData will halt during outages.

MVP-friendly pattern:

allow deposits/withdraw requests using the last accepted NAV for up to N minutes (e.g., 10–30 min), while still blocking claims/payouts if liquidity isn’t there.

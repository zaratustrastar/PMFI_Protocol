You’ve got two separate problems in that log:

1) Withdrawal servicer is trying to place orders without Polymarket L2 auth

This is the core error:

py_clob_client.exceptions.PolyException: API Credentials are needed to interact with this endpoint!

Meaning: in withdrawal_servicer.py, your ClobClient was created but never got L2 API creds set, so post_order() refuses.

Your bot_v7.py does initialize L2 auth successfully (“✅ CLOB client initialized with L2 auth …”), but the withdrawal servicer doesn’t.

Fix (in code): set L2 creds on the CLOB client before posting orders

In withdrawal_servicer.py wherever you build the client, you want something like:

from py_clob_client.client import ClobClient

host = "https://clob.polymarket.com"  # or whatever you're using
chain_id = 137  # Polygon for polymarket CLOB (usually)

pk = os.environ["POLYMARKET_PRIVATE_KEY"]  # or a dedicated TRADING key

client = ClobClient(host, chain_id=chain_id, private_key=pk)

# This is the missing step:
creds = client.create_or_derive_api_key()
client.set_api_creds(creds)

# now post_order() will work


If you already have explicit API creds (key/secret/passphrase), you can set them directly instead of deriving, but the above pattern is the common “just use PK” flow.

Fix (ops): make sure the servicer has the env var

Your logs show you exported POLYMARKET_PRIVATE_KEY for bot_v7.py, but the servicer process might be running in a different shell/systemd/docker env.

Quick check inside the servicer runtime:

echo $POLYMARKET_PRIVATE_KEY


If empty, that’s why it can’t auth.

Important security note: you pasted a real-looking private key in the logs. Assume it’s compromised and rotate it.

2) Your servicer is using a bad NAV cache ($1.0000) while bot is producing ~$0.80

Servicer says:

NAV from bot (cached): $1.000000

But your bot logs clearly show signed NAV around 0.80–0.81/share once buffer is included.

That $1.00 NAV happens in your bot when it can’t read full on-chain state (you have tons of):
429 Client Error: Too Many Requests for url: https://mainnet.base.org/

So the bot sometimes falls back to an incomplete state (buffer read fails → totals wrong → NAV snaps to 1.0).

Fix: don’t let servicer act on stale/invalid NAV

Add a hard guard in the withdrawal servicer:

only accept NAV if:

bot cache timestamp is fresh (e.g. updated < 90s ago)

bot also returns a “status ok” / “breakdown check passed”

roundId matches expected

if NAV is missing/1.0 while on-chain buffer/supply indicate otherwise → pause withdrawals and alert.

Fix: stop hammering https://mainnet.base.org (429)

Use a higher-limit RPC (paid or better free), and also:

increase polling interval

add exponential backoff on 429

cache reads that don’t change every loop (USDC decimals, contract instances, etc.)

batch/multicall where possible

Right now the bot is half-blind intermittently, and your servicer is trusting its cached NAV.

What to do right now (fast path)

Fix L2 auth in withdrawal_servicer.py (add create_or_derive_api_key() + set_api_creds()).

Ensure the servicer process actually has POLYMARKET_PRIVATE_KEY in its environment (systemd/docker env file).

Add a safety check: if bot NAV cache is stale or bot recently hit 429 → do not liquidate / do not service withdrawals.

Switch to a better Base RPC + add backoff.
